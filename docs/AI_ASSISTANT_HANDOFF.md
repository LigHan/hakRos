# ИИ-помощник: прототип и задачи для команды

**Статус:** отдельный экран и API для интеграции. Сервер работает с GigaChat и при настройке получает открытые данные мест из существующего API. Заготовленные ответы удалены: без действительного ключа сервер возвращает ошибку. Основное приложение и общие файлы интеграции пока не изменены. Поиск людей, проверка цен и времени работы не подключены.

## Идея интерфейса

Маскот — небольшая кнопка над нижней панелью. При удержании она увеличивается и подсвечивается; её можно двигать по горизонтали и поднимать вверх, после отпускания она плавно возвращается к панели. Нажатие открывает чат. Первые варианты сообщения — «Есть пара часов» и «Подскажи, куда сходить». Положение и видимость на основных экранах нужно согласовать с владельцами навигации: кнопка не должна закрывать панель вкладок, карту и важные элементы. Кнопка имеет подпись и действия перемещения для скринридера; имя маскота пока не определено.

На отдельном маршруте `/assistant-preview` есть демонстрация. Изображение взято из предоставленного пользователем референса; до утверждения финального ассета компонент показывает его квадратный фрагмент. Для выпуска заменить временный референс на утверждённый компактный исходник маскота с достаточным разрешением и согласованными правами использования.

## Запуск прототипа

В `backend` после `npm ci`:

```powershell
node assistant-dev.js
```

По умолчанию работает отдельный сервер на `127.0.0.1:3001`; команда **не меняет** основной сервер на порту 3000. Затем запустить frontend по `README.md` и открыть `http://localhost:8081/assistant-preview` (используйте фактический адрес Expo, если порт отличается). На Android Emulator тестовый URL использует `10.0.2.2:3001`; на физическом устройстве нужно отдельно разрешить доступ к тестовому серверу и задать `EXPO_PUBLIC_ASSISTANT_URL` — адрес компьютера, доступный устройству. Настройки сети и доступа согласовать с интегратором.

При неработающем сервере или отсутствии ключа интерфейс показывает ошибку и сохраняет текст для повторной отправки. Проверьте `GET /api/assistant/health`; признак `configured` показывает лишь наличие настройки, а не успешное подключение к модели.

## Подключение GigaChat и каталога

В локальном прототипе проверен ответ GigaChat 2 Max через чат с использованием текущего каталога. Для дальнейшей работы перевыпустить ранее опубликованный в чате ключ. Значение нового Authorization Key хранить только в локальной переменной окружения backend или в локальном `backend/.env`, который исключён из Git; не помещать его в `EXPO_PUBLIC_*`, frontend, чаты, логи, PR или документацию. Прототип рассчитан на личный API с `GIGACHAT_API_PERS`; иные типы аккаунтов требуют отдельного согласования и настройки.

Серверу нужны:

- `GIGACHAT_AUTH_KEY` — новый Authorization Key из проекта Сбера;
- при необходимости `GIGACHAT_MODEL` (по умолчанию `GigaChat-2-Max`);
- `ASSISTANT_CATALOG_URL` — адрес API мест, например `http://127.0.0.1:3000/api/posts` при работе обоих серверов на одном компьютере. Адрес задаётся администратором на сервере, а не пользователем чата.

Установить или предоставить процессу официальные сертификаты Минцифры согласно [документации GigaChat](https://developers.sber.ru/docs/ru/gigachat/certificates). Если используется файл с доверенным CA, переменную `NODE_EXTRA_CA_CERTS` нужно задать **до запуска Node.js**. Не отключать проверку TLS. Затем запустить `node assistant-dev.js`, проверить `/health` и отправить сообщение. `configured: true` не подтверждает корректность ключа. При ошибке реального API сервер возвращает ошибку и не подменяет ответ заглушкой.

Каталог выбирает до 12 записей по простому совпадению слов и передаёт модели только публичные название, ID, категорию, адрес и описание. Это предварительная выборка, а не готовый алгоритм поиска: качество нужно согласовать с пунктом 1. Текущая база при первом запуске содержит демонстрационные места; наличие записи не подтверждает актуальность. При запросе цены или близости сервер сообщает об отсутствии данных, не пытаясь выдать подбор по неизвестным критериям; при отказе от учёта бюджета снова обращается к модели. Цены, длительность и время работы не проверяются, а ответ модели может содержать ошибку.

Тестовый сервер не имеет аутентификации и ограничения частоты, а `cors()` разрешает обращения с других источников. Он предназначен только для локальной демонстрации на доверенном компьютере и не должен публиковаться в интернет. Перед настоящим развёртыванием нужны серверная авторизация, ограничение частоты и затрат, согласованная политика CORS и безопасное хранение ключей.

## Контракт API для интегратора

Все пути ниже — контракт данного прототипа, не обещание, что он уже подключён к основному серверу.

`GET /api/assistant/health` → `{ "mode": "gigachat", "configured": true | false }`.

`POST /api/assistant/chat` принимает текст длиной 1–1000 символов и необязательную историю из максимум шести сообщений с ролями `user` или `assistant` и длиной каждого сообщения до 1000 символов:

```json
{
  "message": "Есть 500 рублей и два часа. Чем заняться?",
  "history": [{"role": "user", "content": "Привет!"}]
}
```

Успех: `{ "reply": "...", "mode": "gigachat", "catalogAvailable": true | false }`. Ответ об отсутствии цен или геопозиции формирует сервер и помечает `source: "catalog_constraint"`, без обращения к модели. Некорректный запрос — HTTP 400; недоступная или не настроенная модель — HTTP 503 с безопасным текстом ошибки. История хранится только в состоянии открытого интерфейса и передаётся в GigaChat вместе с ограниченными полями найденных мест. Пользовательские аккаунты не передаются. `catalogAvailable` сообщает о доступности источника, но не о качестве данных или достоверности ответа.

Интегратор пункта 5 может подключить `createAssistantRouter()` из `backend/assistant/router.js` к `/api/assistant` после `express.json()` в основном сервере. В `_layout.tsx` можно добавить `<AssistantLauncher />` из `frontend/components/assistant/AssistantLauncher.tsx` внутри контейнера, где абсолютная позиция привязана к области приложения. После перехода на основной API задать `EXPO_PUBLIC_ASSISTANT_URL` как его базовый адрес. Эти изменения и конфигурацию общего сервера выполняет владелец интеграции после согласования; готовой основной интеграции сейчас нет.

Проверки: `node --test assistant/assistant.test.js` из `backend`, а также `npm run typecheck` и `npm run lint` из `frontend`. Для полноценного выпуска дополнительно проверить экран и сетевую доступность на физическом устройстве, обработку реального ключа и поведение при сетевых ошибках.

## Что нужно от других чатов

| Кто | Что согласовать и реализовать | Как проверить |
|---|---|---|
| Пункт 1 — поиск и подбор | Отдавать помощнику подтверждённые места по интересам и району; согласовать поля `id`, `название`, `категория`, `адрес`, `цена` и `длительность` с единицами. Неизвестная цена/длительность — `null`, бесплатное место — `0`. | Место с неизвестной ценой не выдаётся как гарантированно подходящее под бюджет; бесплатное попадает в бюджет 0. |
| Пункт 2 — карточки и ленты | Согласовать передачу устойчивого ID и переход к карточке места из ответа; не создавать отдельные дубликаты мест. | Кнопка результата открывает правильную карточку и работает при удалённом/недоступном месте. |
| Пункт 3 — пользователи, аккаунты и админка | Определить, что помощник может объяснять по проверенной инструкции; для поиска компании нужны реальные группы/пользователи и согласие участников. Сам ИИ не раскрывает приватные данные и не отправляет приглашения. | В интерфейсе видны только разрешённые группы и данные; отсутствие подходящих вариантов честно сообщается. |
| Пункт 4 — статистика | Согласовать минимум событий, например открытие помощника, успешный ответ, ошибка и переход к месту. Не сохранять текст диалогов, ключи и персональные данные по умолчанию. | Счётчики работают на тестовых событиях, а сбой статистики не ломает чат. |
| Пункт 5 — интеграция и демонстрация | Согласовать контракты, точку подключения маршрута и кнопки, проверить реальный GigaChat, TLS, доступ по сети и права. Обновить `PROJECT_PROGRESS.md` по отчётам; подготовить резервный сценарий без ИИ. | Сквозной путь: запрос → параметры → подтверждённые места → карточка; при ошибке ИИ остаётся доступен обычный поиск. |

## Следующий этап ИИ

Текущий live-режим только ведёт короткий диалог и предлагает общие идеи. После готовности API поиска можно добавлять извлечение интересов, бюджета и времени в проверяемую структуру. Проверку цены, ограничений и выбор реальных карточек выполняет backend по данным каталога; модель не придумывает адреса, цены или людей. До согласования контрактов не считать поиск мест и пати реализованными.
