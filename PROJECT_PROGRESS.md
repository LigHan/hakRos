# hakRos — общий конспект и прогресс проекта

Этот файл — общий рабочий конспект команды из 9 человек и точка передачи контекста между чатами. Здесь хранятся существенные сведения проекта: цели, требования, договорённости, задачи, результаты, проверки, проблемы и история изменений. Файлы кода и первичные материалы остаются на своих местах; здесь сохраняйте содержательную выжимку и ссылки на них.

**Репозиторий:** https://github.com/LigHan/hakRos  
**Инициализация:** 11.11.2026. На момент подготовки репозиторий был пуст; тема проекта, состав команды и условия хакатона ещё не известны.  
**Последнее содержательное обновление** — 11.11.2026. Зафиксированы объединённые изменения карты, друзей и модерации точек.

## Как пользоваться команде

1. Положите этот файл и соседний `AGENTS.md` в корень репозитория и сохраните их в общей ветке. Каждый участник начинает работу со свежей версии общей ветки и этого файла.
2. В начале нового чата с ИИ передайте ему инструкцию ниже. Если ИИ не видит репозиторий или файл, приложите актуальную копию. Доступ к одному чату не означает доступа к остальным.
3. Перед завершением чата передай результаты пункту 5. Пункт 5 обновляет журнал и объединяет записи команды при синхронизации.
4. Перед публикацией своей версии получите изменения команды. При конфликте файла вручную объедините записи обоих участников; не перезаписывайте чужие изменения. Согласуйте противоречивые решения с ответственными и отметьте вопрос в разделе «Открытые вопросы». Удобно назначить одного человека интегратором, но каждый отвечает за свой вклад.
5. Репозиторий публичный. Не записывайте пароли, токены, персональные данные и приватную переписку. Указывайте безопасное название секрета или закрытого ресурса и место его хранения без значения.

### Сообщение для начала каждого чата

Скопируйте в новый чат, заполнив скобки:

> Делай пункт N или задачу Т-XX. Прочитай `AGENTS.md` и описание назначенной работы в `TASKS.md`.

**Важно:** ни этот файл, ни `AGENTS.md` сами по себе не подключают чаты друг к другу и не гарантируют автоматическое сохранение. Чат видит только доступные ему источники. Если запись была только в локальной ветке или в ответе чата, остальные её не увидят, пока изменения не объединены или текст не передан вручную. Проверяйте обновление файла перед завершением работы.

## Подключение участника и Codex

Эта процедура рассчитана на каждого участника отдельно. Codex может установить инструменты, проверить настройки, склонировать проект и подготовить Git в доступной ему среде. **Первичный вход в GitHub и предоставление доступа нельзя гарантированно выполнить без участия владельца аккаунта:** GitHub может запросить вход в браузере, одноразовый код, двухфакторную проверку и подтверждение приложения. Право записи в репозиторий предоставляет владелец GitHub-аккаунту участника. Codex не должен запрашивать у пользователя пароль, токен или код и не должен обходить вход.

### Как запустить настройку в новом чате

Пока репозиторий ещё не открыт, `AGENTS.md` из него автоматически недоступен. Скопируйте в Codex сообщение:

> Настрой на этом компьютере Git и GitHub CLI для работы с https://github.com/LigHan/hakRos. Проверь операционную систему, наличие инструментов, активный аккаунт и доступ к репозиторию. Сам выполни доступные шаги установки, настройки и клонирования, не переустанавливая уже работающие инструменты. Если нужен вход в GitHub или подтверждение, попроси меня выполнить его лично в браузере; не проси присылать пароли, токены или одноразовые коды. После подключения открой или используй локальную копию проекта, прочитай `AGENTS.md` и `PROJECT_PROGRESS.md`, проверь состояние и сообщи результат. Не отправляй изменения в GitHub без отдельного поручения.

Если Codex работает не на компьютере участника, а в облаке или другом окружении, авторизация и установленные программы локального компьютера могут быть ему недоступны. Настройку и проверку нужно выполнять в той среде, в которой Codex будет работать; при отсутствии доступа к ней попросите участника выполнить необходимые шаги.

### Порядок действий для Codex

1. Проверь ОС, наличие `git` и `gh`, текущий каталог и существующие рабочие копии. Переиспользуй подходящую копию и не перезаписывай несохранённую работу. На Windows при отсутствии инструментов можно использовать `winget install --id Git.Git` и `winget install --id GitHub.cli`; для другой ОС выбери подходящий доступный способ. Если установка недоступна или требует системного подтверждения, объясни участнику нужный шаг. После установки новая сессия терминала или перезапуск Codex могут понадобиться для обновления `PATH`.
2. Выполни `gh auth status`, не запрашивая и не выводя токены. Если входа нет или активен не тот аккаунт, помоги участнику запустить `gh auth login --web --git-protocol https`: он сам вводит код из терминала на странице GitHub и подтверждает вход. Используй видимый терминал или инструкции участнику, если код нельзя безопасно показать иначе. Затем настрой Git через `gh auth setup-git`. Если вход уже настроен, повторная авторизация не нужна.
3. Проверь, что аккаунт участника действительно имеет право записи в `LigHan/hakRos`. Если прав нет или они не подтверждены, сообщи об этом: владелец должен предоставить доступ, а участник — принять приглашение. Защита ветки может требовать pull request даже при праве записи. Не проверяй право отправкой пробного коммита без задачи и не выдавай право на чтение за право записи.
4. Настрой автора коммитов, только если данных не хватает: уточни имя и GitHub-почту или `noreply` участника, предпочитай настройки конкретного репозитория и не выдумывай личные данные. Склонируй репозиторий в согласованное доступное место, если подходящей копии нет. Для пустого репозитория сообщи, что общая ветка появится после первого коммита; не считай её наличие подтверждённым заранее.
5. После появления файлов прочитай этот документ и `AGENTS.md`. Работай в отдельной ветке, перед изменениями получай актуальное состояние, при объединении сохраняй данные других участников. Публикуй коммиты, ветки и pull request только по поручению пользователя и сообщай о результате. При ошибках сохраняй изменения и объясняй, что необходимо исправить.

## 6. Устройство проекта и запуск

- **Архитектура** — Expo Router во `frontend/`, Express API и SQLite в `backend/`.
- **Версии** — Expo 58.0.23, React 19.3.0, React Native 0.88.1, TypeScript 6.0.3, Express 5.3.0 и sqlite3 6.0.1. Подробности в [DEPENDENCIES.md](DEPENDENCIES.md).
- **Запуск** — `npm ci` в каждой папке, `npm start` для API и `npm run web` для интерфейса. Адреса и переменные окружения описаны в [README.md](README.md).
- **Данные и API** — `GET /api/posts`, `GET /api/posts/:id`, `GET /api/stories`, `POST /register` и `POST /login`. При первом запуске SQLite создаёт демонстрационные данные. Категорию места из API используют поиск и лента.
- **Карта** — MapLibre GL JS, данные OSM через OpenFreeMap, WebView на мобильных устройствах. Нужны запущенный API и доступ к интернету; ключ Яндекс Карт для подложки не нужен. Маршрут и поиск адреса могут открывать Яндекс Карты. [README](README.md), [настройка границ](backend/map-assets/regions-ru.md).
- **Точки и доступ** — `map_places` хранит координаты и статус; новая точка видна автору и подтверждённым друзьям из таблицы `friendships`. Автор отдельно отправляет её на проверку; локальный администратор одобряет или отклоняет её в разделе «Места». Одобренная точка видна всем. Старые пользовательские точки при миграции становятся приватными.
- **Геопозиция** — включается пользователем на экране карты, хранится в памяти API и устаревает через пять минут. Сейчас её видят все авторизованные пользователи: это не выполняет требование Т-17 о выбранных друзьях. Лента «Рядом» использует общий список API; админка доступна в локальном деморежиме.
