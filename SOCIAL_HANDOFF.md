# Т-11–Т-16: состояние и интеграция

Ветка работы: `task/design-concepts`. Изменения пока локальные. Сверена общая ветка `main` на `2dc315f`: Т-10 с друзьями и подписками объединена. Описание API и ограничений Т-10 находится в [CONNECTIONS.md](CONNECTIONS.md).

## Что сделано

- **Т-11:** после входа обычный пользователь попадает на `/` — страницу рекомендаций, которая по решению пользователя является главной. Отдельная прежняя главная удалена. Полноценной ленты публикаций друзей и подписок пока нет.
- **Т-12:** начальный экран показывает доступные публичные истории подписанных заведений: `frontend/lib/connections-feed.ts` сопоставляет `story.postId` с `subscriptions[].placeId`. Материалы друзей не показываются: существующая модель не содержит нужной связи с автором. Клиентская фильтрация публичных данных не является серверной проверкой доступа к приватным материалам.
- **Т-13:** кнопка «+» открывает выбор публикации или истории; отмена возвращает на исходный экран. Есть раздельные локальные текстовые черновики на устройство и аккаунт. Экран сообщает, что публикация пока недоступна; вход возвращает к выбранному черновику.
- **Т-14:** новые лайки, комментарии и репосты с серверной проверкой ещё не реализованы. Существующие лайки мест не заменяют их.
- **Т-15:** начальный экран показывает доступные места из API, переход в карточку, фильтры, загрузку, ошибку и пустую выдачу. Персональное ранжирование не реализовано; это отмечено на экране. Ссылка «Места рядом» открывает существующий экран.
- **Т-16:** нижняя панель: рекомендации → карта → «+» → поиск → профиль. Для гостя профиль открывает вход, создание предлагает войти. Старый адрес `/recommendations` перенаправляет на `/`.

## Что необходимо согласовать с Т-01 и владельцами смежных задач

1. Утвердить модель публикации и истории: ID автора, ID заведения, доступные поля и медиа, аудиторию, срок истории, порядок и правила удаления. Для Т-11/12 нужна серверная выдача только разрешённых материалов и проверка прав на каждый материал, включая публикации друзей.
2. Утвердить API публикации с устойчивым ключом повтора, чтобы повтор после ошибки не создавал дубликаты. Локальный черновик не отправляется и не синхронизируется.
3. Утвердить API и хранение лайков, комментариев и репостов; проверять права на сервере, включая видимость оригинала при репосте, и проверить сохранение после перезапуска.
4. Согласовать ранжирование рекомендаций с Т-02 и Т-04; текущий список не персонализирован.

## Проверка

`node --test frontend/tests/connections-feed.test.mjs` запускается на Node.js 24. Тесты проверяют сопоставление по ID, отсутствие подписок и порядок. На отдельной тестовой базе также проверено, что история подписанного заведения отбирается, а история другого заведения исключается. В браузере на этой базе проверены вход, рекомендации, профиль, настройки, подписка на заведение и счётчик подписок. Полные серверные сценарии Т-11–Т-14 и проверка интерфейса на физическом устройстве после последних изменений ещё требуются.
