## Как пользоваться команде

1. Положите этот файл и соседний `AGENTS.md` в корень репозитория и сохраните их в общей ветке. Каждый участник начинает работу со свежей версии общей ветки и этого файла.
2. В начале нового чата с ИИ передайте ему инструкцию ниже. Если ИИ не видит репозиторий или файл, приложите актуальную копию. Доступ к одному чату не означает доступа к остальным.
3. Во время работы фиксируйте значимые результаты, а перед завершением чата обновляйте разделы текущего состояния и добавляйте запись в журнал. На запись в общую ветку изменения попадают только после обычной синхронизации Git и, при необходимости, принятия pull request.
4. Перед публикацией своей версии получите изменения команды. При конфликте файла вручную объедините записи обоих участников; не перезаписывайте чужие изменения. Согласуйте противоречивые решения с ответственными и отметьте вопрос в разделе «Открытые вопросы». Удобно назначить одного человека интегратором, но каждый отвечает за свой вклад.
5. Репозиторий публичный. Не записывайте пароли, токены, персональные данные и приватную переписку. Указывайте безопасное название секрета или закрытого ресурса и место его хранения без значения.

После подключения открой или используй локальную копию проекта, прочитай `AGENTS.md` и `PROJECT_PROGRESS.md`, проверь состояние и сообщи результат. Настройку и проверку нужно выполнять в той среде, в которой Codex будет работать; при отсутствии доступа к ней попросите участника выполнить необходимые шаги.

### Порядок действий для Codex

1. Проверь ОС, наличие `git` и `gh`, текущий каталог и существующие рабочие копии. Переиспользуй подходящую копию и не перезаписывай несохранённую работу. На Windows при отсутствии инструментов можно использовать `winget install --id Git.Git` и `winget install --id GitHub.cli`; для другой ОС выбери подходящий доступный способ. Если установка недоступна или требует системного подтверждения, объясни участнику нужный шаг. После установки новая сессия терминала или перезапуск Codex могут понадобиться для обновления `PATH`.
2. Выполни `gh auth status`, не запрашивая и не выводя токены. Если входа нет или активен не тот аккаунт, помоги участнику запустить `gh auth login --web --git-protocol https`: он сам вводит код из терминала на странице GitHub и подтверждает вход. Используй видимый терминал или инструкции участнику, если код нельзя безопасно показать иначе. Затем настрой Git через `gh auth setup-git`. Если вход уже настроен, повторная авторизация не нужна.
3. Проверь, что аккаунт участника действительно имеет право записи в `LigHan/hakRos`. Если прав нет или они не подтверждены, сообщи об этом: владелец должен предоставить доступ, а участник — принять приглашение. Защита ветки может требовать pull request даже при праве записи. Не проверяй право отправкой пробного коммита без задачи и не выдавай право на чтение за право записи.
4. Настрой автора коммитов, только если данных не хватает: уточни имя и GitHub-почту или `noreply` участника, предпочитай настройки конкретного репозитория и не выдумывай личные данные. Склонируй репозиторий в согласованное доступное место, если подходящей копии нет. Для пустого репозитория сообщи, что общая ветка появится после первого коммита; не считай её наличие подтверждённым заранее.
5. После появления файлов прочитай этот документ и `AGENTS.md`. Работай в отдельной ветке, перед изменениями получай актуальное состояние, при объединении сохраняй данные других участников. Публикуй коммиты, ветки и pull request только по поручению пользователя и сообщай о результате. При ошибках сохраняй изменения и объясняй, что необходимо исправить.
